<objective>
Fork the Claude-Code-Usage-Monitor upstream repository and lay out all source files
at the repo root (per D-01). Create a root-level `monitor.py` entry point (per D-02)
that delegates to the upstream package. Configure pyproject.toml so the package name
is `token-tracker` (not the upstream name) to avoid conflicts.

Purpose: Without the upstream code present there is nothing to port. This plan
establishes the baseline that all subsequent plans fix and extend.

Output: All upstream Python source modules at repo root, `python monitor.py` runnable
(may show path errors on Windows — that is expected and fixed in Plan 02).
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Upstream GitHub → local disk | Code fetched from third-party repository; must inspect for malicious content before execution |
| monitor.py → subprocess/shell | Entry point must not exec shell strings from argv without validation |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-01 | Tampering | Upstream source clone | mitigate | Clone via HTTPS from the known repo URL (github.com/Maciek-roboblog/Claude-Code-Usage-Monitor); verify no `setup.py` post-install hooks execute arbitrary code |
| T-01-02 | Information Disclosure | pyproject.toml | accept | Package metadata is not sensitive; no credentials or tokens stored here |
| T-01-03 | Elevation of Privilege | monitor.py entry point | mitigate | Entry point must only import and call upstream main(); must not accept shell-injection via CLI args — leave arg parsing to the upstream argparse layer |
</threat_model>

Create two files at the repo root:

--- FILE 1: pyproject.toml ---

Start from the upstream pyproject.toml. Make these changes:
  1. Set `name = "token-tracker"` (prevents conflict if upstream is also installed)
  2. Set `version = "0.1.0"`
  3. Keep all upstream `dependencies = [...]` entries exactly as-is
  4. Add `"tzdata"` to the dependencies list (Windows timezone database — required by pytz on Windows)
  5. Remove any `[project.scripts]` entry pointing to the upstream package name; replace with:
       [project.scripts]
       token-tracker = "monitor:main"
  6. Keep `requires-python = ">=3.11"` (or set it if absent)
  7. Keep `[build-system]` section (setuptools/hatchling — whatever upstream uses)

The final pyproject.toml MUST contain:
  - `name = "token-tracker"`
  - `version = "0.1.0"`
  - `tzdata` in dependencies
  - `requires-python = ">=3.11"`

--- FILE 2: monitor.py (root-level entry point, per D-02) ---

Read the upstream's main entry point to understand what function to call. The typical
pattern in the upstream is a `main()` function in a module like `claude_monitor/main.py`
or directly in a top-level script.

Create monitor.py that:
  1. Sets up Windows stdout/stderr encoding at the top (before any rich imports):
       import sys
       if sys.platform == "win32":
           import io
           sys.stdout = io.TextIOWrapper(sys.stdout.buffer, encoding="utf-8", errors="replace")
           sys.stderr = io.TextIOWrapper(sys.stderr.buffer, encoding="utf-8", errors="replace")

  2. Imports the entry-point function from wherever the upstream defines it, e.g.:
       from monitoring.orchestrator import main   # adjust to actual upstream location
     OR if the upstream uses a __main__.py pattern:
       import runpy; runpy.run_module("monitoring.orchestrator", run_name="__main__")

  3. Defines a `main()` function that calls the upstream entry point

  4. Has the standard `if __name__ == "__main__": main()` guard

  If the upstream does not have a clean `main()` function and instead runs code at module
  import time, create a thin wrapper that uses `subprocess` to run the upstream script —
  but prefer direct import if at all possible.

  Exact path: C:/Users/justin.rhoda/token.tracker/monitor.py
